# 刷抖音（douyin-scroll）

让桌宠替你「刷」抖音：从本机抖音桥接读取推荐流，按你的兴趣挑一条，念一句
`刷到：标题 @作者`，挑得出来还会顺口念一条热评。可以随时 `browse` 浏览本次
抓到的推荐、`pick` 自己挑一条，再翻评论区、挑评论和回复。**写操作（点赞 /
收藏 / 评论点赞 / 评论 / 回复）默认关闭**，开启后也必须先过插件内置的守门脚本。

## 它依赖什么

插件自身不联网，也读不到浏览器。它只通过主应用的 `bridge` 权限向**本机**的
抖音桥接服务发请求，剩下的（请求、桌宠动作、状态持久化）都由宿主执行。

宿主就是主应用里的脚本运行时。**Flutter 版 0.1.x 还没有接上运行时**：现在把
这个插件装进主应用，它只会出现在插件列表里并标注「已安装 · 运行时未接入」，
下面这些端点一个都不会被调用。0.1.7 及更早的 Electron 版本跑过它。

桥接服务需要由你自己运行（例如一个本机小服务），端点如下：

| 方法 | 路径 | 要求 |
| --- | --- | --- |
| `GET` | `/feed?limit=20&comments=1` | 返回 `{ "items": [ { "id", "title", "author", "url", "hot"?, "comments"? } ] }` |
| `GET` | `/status` | 返回 `{ "ok": true, "account": "..." }`，可选 |
| `POST` | `/like` | `{ "id": "..." }` |
| `POST` | `/favorite` | `{ "id": "..." }` |
| `POST` | `/comment-like` | `{ "id": "..." }`，`id` 是评论 id |
| `POST` | `/comment` | `{ "id": "...", "text": "..." }` |
| `POST` | `/reply` | `{ "target": "...", "text": "..." }` |

`items[].id`、`comments[].id`、`comments[].replies[].id` 必须是 `[A-Za-z0-9_-]{1,64}`，
`url` 必须是 `https://` 才会被采纳。评论形如：

```json
{
  "id": "c-1001",
  "author": "沙箱研究所",
  "text": "编译参数那四个 --export 是真的容易漏",
  "likes": 312,
  "replies": [{ "id": "r-1001", "author": "某鱼", "text": "等你交作业" }]
}
```

写端点收到的是 JSON 正文（插件不发请求头，所以示例桥接不校验 `Content-Type`）。
仓库自带的 `tools/bridge.ts` 就是一份可直接运行的示例：

```sh
node tools/bridge.ts            # http://127.0.0.1:8787，读 tools/feed.json
node tools/bridge.ts --port 8787
```

示例会把收到的写请求打印到终端，并记在内存里：`GET /log` 可以看到
`{ "writes": [{ "at", "action", "target", "text"? }] }`。**它不会真的去操作抖音**——接真实账号时务必在
你自己的服务里再做一次鉴权与限流。

## 设置项

| id | 类型 | 说明 |
| --- | --- | --- |
| `bridgeUrl` | url | 桥接地址，例如 `http://127.0.0.1:8787` |
| `intervalSeconds` | number | 刷新间隔，5–300 秒，默认 20 |
| `interestBoost` | boolean | 是否优先推送命中兴趣关键词的内容，默认开 |
| `allowWrites` | boolean | **写操作总开关**，默认关 |
| `autoFavorite` | boolean | 命中兴趣时自动收藏，默认关；仍受总开关与守门约束 |
| `autoReply` | boolean | 命中兴趣的评论自动回复，默认关；仍受总开关与守门约束 |
| `commentText` | text | 你亲手写的评论原文，`comment` 命令只发这一句；不合规会被拒发，绝不改写（规则见「守门脚本」第 3 条） |
| `replyText` | text | 你亲手写的回复原文，`reply` 命令与自动回复只发这一句；规则同上 |
| `dailyWriteLimit` | number | 每日写入额度，1–50，默认 5 |
| `writeCooldownSeconds` | number | 两次写入之间的冷却，10–600 秒，默认 60 |

兴趣关键词来自主应用的「兴趣」设置，命中标题加分高于命中作者。

## 命令

- `next`：立刻刷一条。
- `reset`：清零累计计数、今天已占用的每日写入额度与去重记录，清除在途 / 冷却状态，
  并清掉本次抓取的快照与选择游标（写入序号照旧保留，只在不可用时重播种）。
- `stats`：让桌宠念出累计刷了多少条、今天占用了几次每日写入额度。这个数字是
  **已占用**的次数：含已被后来的写入顶替、结果尚未确认的写入；仍在途且尚未被
  顶替的那一笔要等**成功**回执或被顶替才计入（失败回执不占，回执读不出成败时
  按占用一次算）。
- `browse`：把本次抓取保留的推荐按每页 3 条念出来；再发一次就是下一页。
- `pick`：在本次抓取保留的推荐里依次选中下一条。
- `comments`：念出**选中视频**的评论区（最多 3 条，只念能念的）。
- `peek`：显式查看最近一次被拦下的内容。被拦下的正文默认一个字都不念，`peek` 是
  唯一出口；详细规则见「守门脚本」下的「`peek` 的目标与回退」。
- `pick-comment`：依次选中下一条评论。
- `pick-reply`：选中评论下的下一条回复。
- `like` / `favorite`：对**选中的视频**点赞 / 收藏。
- `comment-like`：对**选中的评论**点赞。
- `comment`：对选中的视频发一条评论，正文就是 `commentText`。
- `reply`：优先回复**选中的回复**；没选回复时回复选中的评论；都没选时退回
  本次抓取里念出来的那条热评。正文就是 `replyText`，不会自动改写成别的话。

抓取一次会留下一个小快照（最多 6 条视频、每条 3 条评论、每条评论 2 条回复）。
评论与回复的原文超过 300 字节就整条不进快照（`Snapshot.max_comment_bytes`），
`browse` / `pick` / `comments` / `peek` 与写入都够不到它，不是「只截断展示」。
`browse` / `pick` / `comments` 只认这个快照里的编号；写完一条视频后快照不会
凭空换成别的内容，选择游标也会在每次抓取后归零。

`browse` / `pick` / `pick-comment` / `pick-reply` 也接受 `args.index`（1 起）直接
定位，越界会拒绝而不是绕回。是否能把编号传进来取决于宿主：宿主只发命令名时，
就一直用重复调用翻下一条。

## 自主写入：收藏与回复

两个开关都默认关闭，都要先开「允许写入」：

- `autoFavorite`：视频本身命中兴趣时自动收藏。
- `autoReply`：**被念出来的那条评论**命中兴趣时，先看它下面有没有可用回复：
  桥接顺序里的第一条可用回复不是可疑内容就回复它，否则回复这条评论，正文
  都是 `replyText`。

这两个动作有一条共同约束：**一条视频最多只自动写一次**，且回复优先于收藏——一条
视频同时满足两者时只发回复，不会又收藏又回复。所有自动写入和命令走同一个守门，
只差在拒绝时念不念理由：命令会把理由念出来（按钮是你按的），自动路径不念；普通
拒绝连状态栏都不更新（`tick` 抓回来的一句话不该替你在桌面上嚷「每日写入额度用
完了」）。有正文但原样发不出去是例外：状态栏留一行完整提示「自动回复没发出去：
设置里的回复正文不合规，手动执行一次 reply 会说明原因」；只要这条正文仍然不合规，
这些视频每个 tick 都会被重新拦下，不会改走自动收藏——回复优先于收藏，仍然满足
「一条视频最多只自动写一次」。`replyText` 为空时
自动回复根本不触发，也就不会有「正文不合规」那行提示，状态栏仍是抓到的那一条。
被拒的写入不启动冷却、也不计数：只有真正发出去的写入才占冷却；每日写入额度在
写入被后来的新 token 顶替那一刻就先记一笔（宁可高估），迟到的成功回执只确认结果、
不重复计，失败也不退回，慢桥接不能靠反复超时绕过封顶。

许可只由上面两个条件决定，热度与点赞不是筹码：点赞再多、热度再高，也只能让这条内容
更容易被刷给你看，换不来一次自动写入。

关掉 `interestBoost` 只改推荐排序，挑选仍按热度来，所以只有被挑中的那条视频标题带
关键词时才会自动收藏——挑中的那条没命中，这一轮就不写。评论侧的挑选不看这个开关：
念哪条评论按兴趣 + 点赞来，点赞被折叠到很小的量级，所以一条零赞但命中兴趣的评论不会
被一万赞的闲话挤掉，「被念出来的评论命中兴趣」才可能真的成立。

自动路径在**守门拒绝**时唯一会念出来的是「写入序号用尽」：这不属于「这一条不该写」，
而是插件的账本坏了——而且只念一次，回复分支说过之后收藏分支就停手，不会让同一轮出现
两条一模一样的提示。正文不合规也一样闭嘴，只留上面说的那行状态提示。真发出去的写入
照常播报回执结果：成功、失败、或者认不出动作。

## 守门脚本：为什么评论不能「自由发挥」

推荐流、评论、回复全是陌生人写的文本。这类文本最危险的用法不是「写得不好」，
而是**当成指令**：一句话藏个「忽略之前的设定」，或者塞一堆看不见的字符把真正的
句子藏起来；长上下文里再强的角色提示词也可能被注意力偏移带走。所以这里不靠
提示词，靠代码：

1. **写操作只有一条合法路径**：`command`（或你明确打开的自动收藏 / 自动回复）
   → 守门通过 → 发出请求。feed 文本不能决定**写什么、写给谁**：目标 id 只认本次
   快照，正文只认设置里的原文。它唯一能影响的是「这一轮要不要触发」——你亲手
   打开自动开关、且这一条命中兴趣时，`tick`、`next` 与 `effect-result` 带回的
   推荐每轮至多带出一笔；开关关着时 feed 里的任何措辞都带不出一次写入。匹配到
   在途回执的那一轮直接结束，不做自动写入。
2. **目标必须同时「格式合法」与「有来源证明」**：`lastId` / `lastCommentId` /
   `lastReplyId` 只能由选择命令或上一次成功抓取写入，且写请求发出前还要确认
   这个 id 真的出现在最近一次抓取的 `videoIds` / `commentIds` / `replyIds`
   快照里。id 必须匹配 `[A-Za-z0-9_-]{1,64}`。桥接文本无法伪造一个「写到哪里」，
   伪造一个 `lastId` 也过不了来源证明。
3. **正文只能是你手写的原文**：`commentText` / `replyText` 逐字发送，绝不拼接
   feed 里的标题、评论或回复。命令本身也没有「内容」参数。发送前只判定能不能
   **原样**发：必须是有效 UTF-8，不含控制符、零宽字符、软连字符（U+00AD）、双向
   控制符（含 U+061C）、行分隔符（U+2028 / U+2029）、空白填充符（U+115F /
   U+1160、U+180E、U+2800、U+3164、U+FFA0）与 Unicode 标签字符，不含换行 /
   回车 / 制表符，不是纯空白，且不超过 200 字。emoji 组合符（ZWJ U+200D、变体
   选择符 U+FE00–U+FE0F）放行：它们只决定字形怎么拼，带不了载荷；但一条只有
   组合符的正文仍算「没有可见内容」，照样拒发。不合规就拒发并说明理由，绝不删
   字符、压空白或截断后照发——清洗后发送会让发出去的那句变成你没写过的话。命令
   路径把理由念出来；自动路径的规则见上面「自主写入」那一节。
4. **回执归属**：每一笔写入都带自己的序号（回执 id 形如 `write:favorite:7`），
   只有回执 id 与在途 token 逐字符相同才算这一笔结束。动作名相同但序号不同、
   同一 token 的重复投递、`reset` 之后才到的旧回执，以及根本没有在途写入时
   收到的写回执，只要不在超时名单上，就一律忽略，不改**写入**状态（在途标记
   与当日已占用的每日写入额度），也不播报动作结果（单独到达时只回一句
   「已忽略」），但同批 feed 照常处理。匹配的回执结束本轮，同批带回的 feed 不
   顺带处理，留到下一次抓取；同批里若还夹着超时名单上的旧回执，也一并结算，
   但结算结果只播报，不再改计数。任何结算了旧回执的一轮都不处理同批 feed。
   桥接地址为空时写入直接不发，但回执照样匹配并清掉在途标记。序号在正常区间内
   跨 `reset` 保持单调，重置后也不会复用旧 token；序号需要重播种时，从「在途
   token 与超时名单里的最大序号」往上抬，正常情况下重置后第一笔比它们都大，
   不会和谁撞号。顶在 i64 上限那种情况要连按两次 `reset`，完整的重播种条件见
   「边界情况」下的「`reset` 是解卡出口」。
5. **冷却、超时、额度与时钟**：
    - **冷却与在途**：冷却从**发出**时起算，只有真正发出的写入才占冷却。在途窗口
      （120 秒）内的第二笔由在途检查直接拦下，先于冷却判定。120 秒没回执按超时
      处理，避免一次丢包永久锁死。超时按固定窗口兜底：原请求可能已经在桥接侧
      成功，重试可能产生重复点赞 / 收藏 / 评论，所以冷却照旧生效——写不通的端点
      同样占用冷却，不能被连续重试。默认冷却 60 秒比在途窗口短，真正隔开超时重试
      的是在途窗口本身；只有把 `writeCooldownSeconds` 配到超过 120 秒，冷却才会
      继续压住超时后的第一笔（两个窗口都用严格小于比较，正好 120 秒时一起过期）。
    - **超时与超时名单**：超时后重试会把旧 token 记进有界名单（最多 3 个，最旧的
      先丢，重复的 token 不重复占位），名单只用于事后确认那笔到底成没成。迟到回执
      只播报结果——成功不重复计，失败也不退回；回执里读不出 `ok` 时只摘名单、
      如实说「无法确认」，不替桥接编造成败；一批里成功、失败、无法确认混在一起时
      有几类念几类，不会把「无法确认」的条目悄悄吞掉。在途那一笔的回执读不出 `ok`
      时只清在途标记、如实说「无法确认成败」，但**照样按占用一次每日写入额度**：
      这一笔还没计过数，不占的话，一个只回 `{id}` 不回 `ok` 的畸形桥接就能让每日写入
      额度永远不涨。名单上都不是在途那一笔，所以若当前这笔还在等回执，会再补一句
      「现在这笔还在等回执」。
    - **每日写入额度与日期桶**：这笔额度在被顶替那一刻就记进**顶替当天的桶**——原
      请求哪怕前一天发出，也计在顶替发生的这一天，不回填到旧的日期桶。自动写入走
      同一份守门：顶替一笔超时写入
      时旧账与新账都要预留额度，额度只够一笔时就不发。每日写入额度按 UTC 日期桶算，
      只有桶比今天旧才算换天归零；桶被写到未来（手改状态或系统时钟前跳）一律按
      同日处理，宁可多压到真实换天前，也不会因为一次前跳把每日写入额度重新打开。
    - **时钟回拨与坏状态**：时钟回拨（当前时间早于记录的发出时间）既不算在途过期，
      也不算冷却已过：两者都按未结束拦住，并把时间戳重锚到当前时间，最多多等一个
      窗口 / 一次冷却，不会把写入锁死到只能 `reset`。回执事件与 `reset` 自己不重锚
      （它们要删除同一批状态键，先写后删会被合并吞掉），回拨要等下一个普通事件
      （如 `tick`）才修正，这中间写入照旧被拦住。在途标记在但没有可用时间戳时
      **按在途拦住**：没有证据说明旧请求已经结束，宁可等回执或 `reset`，也不放
      第二笔出去。重锚写在回包里，要等宿主合并 state 才对下一次事件生效，所以
      回拨发生的那一轮仍被拦住，下一次普通事件起才恢复。
6. **显示前清洗（只管展示通道）**：正常播报的桥接文本进入桌宠嘴里之前都按第 3 条
   那份清单删掉不可见字符（emoji 组合符同样除外），空白压成单空格，再按字符数截到
   60 字（`Guard.max_feed_text`）。截断是静默的：不加省略号，也不劈开多字节字符；
   正文不是合法 UTF-8 时整段按空文本处理。看不见的东西念不出来，也撑不长上下文。
   60 字只管正常播报：可疑条目另存一份 200 字的净化副本（`Snapshot.peek_chars`），
   只有显式 `peek` 会把这份副本念出来；写守门也会重扫它判一次，但不展示。传出正文
   不在这条通道上：它走 `bodyRefusal`，只判定、不改写，两条通道的规则故意不同。
7. **可疑内容默认拦下、`peek` 才显式查看**：视频标题、作者、评论、回复先过归一化
    检测。逐字扫描：先看有没有不可见字符，有就当场命中；再跳过两类不承载字符的
    东西：emoji 组合符
   （ZWJ U+200D、变体选择符 VS1–VS16，也就是 U+FE00–U+FE0F）与全部 Unicode 组合
   标记（`General_Category=Mark`，Mn / Mc / Me 共 333 个区间，含补充变体选择符
   VS17–VS256；照 Unicode 18.0 属性数据生成，18.0 新增的 12 段（共 37 个码点）也
   已并入；`test-plugin.ts` 按码点逐个穷举，运行时 Unicode 版本比表新就点名没覆盖
   到的码点）。组合标记是叠在前一个字形
   上的附标与附点，例如组合变音符，以及泰文 / 藏文 / 缅甸文 / 高棉文 / 孟加拉文 /
    泰米尔文等文字里的元音符号、附标与附点。剩下的字符折全角与常见同形字，同时产出
    两张比对视图：紧凑视图
   去掉空白、标点与符号（含 emoji），比对「忽略之前」「ignore previous」这类词形
   标记；形状视图保留标点、只压空白，比对 `system:`、`POST /`、`http://` 这类靠标点
   成形的标记。任一视图命中就判为可疑（「无视以上」「从现在开始你」「系统提示词」
   属于词形标记）；往词中间塞 ZWJ、变体选择符或任意一个组合标记，再拼 `system:`、
   `ignore previous` 这类写法，同样命中。检测把整段文本从头扫到尾，不设「扫到第
   几个字就收工」的额度：塞空白、塞组合符都推不出扫描范围。唯一的上限是大小：
   输入超过 8 KB 直接判可疑——这个上限管的是**抓取时的完整原文**；第 6 条的 60 / 200
   字只是播报与 `peek` 的展示副本上限，约束不了检测输入。超长文本整条拦下，不存在
   「没扫到的尾巴算干净」。
   不可见字符是当场命中。命中后桌宠**默认**只念「疑似注入，已拦下」，正文一个字都
   不进 `say` 或 `status`；单条播报后面再补一句「（发 peek 看被拦下的内容）」，`browse` /
   `comments` 这种列表只在末尾说一次。唯一的例外是用户显式发 `peek`：那时念的只是
   抹掉不可见字符的净化副本，而且依旧只当素材。被标记的条目也不会触发
   自动收藏或自动回复。手动命令同样被统一守门拒绝：不允许对可疑视频点赞、收藏、评论，
   或对可疑评论 / 回复点赞、回复。作者名单独可疑、标题干净时也算这一条可疑，`peek`
   会明说被拦下的是作者名，再把标题与作者名分开念。防护标记只由插件在抓取时按
   **完整原文**算出，写守门不信任命令参数。快照里整条 `suspect:true`、或拆分字段
   里的 `suspectBody:true` / `suspectAuthor:true` 都按可疑拦住；单独的
   `suspectBody:false` 不能否定整条 `suspect:true`——只有 `suspectBody` 与
   `suspectAuthor` 两个拆分字段都在、且不与整条 `suspect:true` 相矛盾时（两个都写
   `false` 而整条仍可疑，就不认拆分字段），才承认其中的 `false` 是抓取时的结论。它还会
   把当前快照里的那条内容重新拼成 `peek` 目标再判一次。副本重扫只能补上漏标的命中，
   存下来的 `true` 照旧按可疑拦住——副本本身有限（见第 6 条的两处上限），落在副本
   之外的命中只能靠抓取时那份标记兜住，所以抹掉布尔值也放不出副本里仍带注入特征的
   内容。

这些规则写死在 `src/main.zig` 里，没有设置项可以关掉。`scripts/test-plugin.ts`
会把注入样本喂进编译好的 `plugin.wasm`，断言它们一个写请求都发不出来。

### `peek` 的目标与回退

快照给可疑条目多留一份净化副本（按第 6 条清洗：不可见字符抹掉，emoji 组合符与
组合标记保留），所以 `peek` 看到的是被拦下那段文字的**净化副本**，不是原始文本；
副本只留前 200 字，命中特征的位置可能落在 200 字之后，那部分看不到。念出来的内容
只当素材，不会变成任何指令，也不会触发任何写操作。

作者名走同一条路，但播报用的作者名副本只有 24 字（`Guard.max_author`），命中点完
全可能落在第 24 字之后：所以作者名可疑时另存一份 200 字的净化副本（`peekAuthor`），
`peek` 优先读它，念出来的才是「为什么可疑」而不是一段干净前缀。读取时两段副本都
会按 200 字上限再截一次，被宿主或用户改长的 state 撑不爆一句话。读取端会整段校验
UTF-8：副本开头就坏时，不念原文，只写「（副本不是合法 UTF-8，无法显示）」；坏字节
在副本中途时，念到坏字节之前的合法前缀为止。

`say` 整句上限 400 字，两份净化副本各自接近 200 字、拼进同一句超过 400 字时按字截
断并补「…」：先念的那段先占位，给后面的固定串（`；作者名也可疑：「` 这样的小标
题、以及收尾引号）和另一段副本留够宽度，不会被整段吞掉。但留出的宽度就是实际可见
的字数：两段都可疑时正文最多约 158 字、作者名约 200 字；只有作者名可疑时作者名约
171 字；只有正文可疑时作者名约 166 字。命中点可能正好落在截断之后，这时 `peek`
只能给出截断处的「…」，看不到触发特征本身。

所有可疑节点的 `peekText` / `peekAuthor` 还受一个 4KB 的快照总预算约束
（`Snapshot.peek_budget_bytes`）：这个额度必须为快照本身的字段和来源 id 留出空间。
预算内先到的可疑条目保留 200 字副本，超出的条目只留可疑标记，`peek` 仍能读到快照
保留的短标题或正文，但看不到那份 200 字原因副本。测试覆盖 6 条视频、18 条评论、
36 条回复全入选的上限；实际 state 仍须受宿主 48KB 限制。

插件只记**一个指针**：最近一次被拦下的是哪一条。`tick` 每轮按视频 → 评论 → 回复
的顺序重记一次（回复是自动回复的目标，正文本身不念出来，被拦下时靠 `peek` 才看
得到），**三类都真正评估过且都不可疑时才清空**；选中的干净视频没有可用评论或回
复时，缺的哪一层不算「干净」，指针原样保留。整页都已看过、这一轮一个字都不念时
一层都没评估，指针同样保留。`browse`、`comments` 取本页第一条可疑的，只在
真的见到可疑条目时才记——翻到干净的一页保留旧指针。
`pick`、`pick-comment`、`pick-reply` 同样只有选中的条目可疑时才写，选中干净条目
不写也不清。所以先选中一条可疑内容、再随手选几条正常内容，`peek` 依旧找得回那条
被拦下的内容。

指针（以及回退扫描）在 `peek` 时都会回到当前快照重新核对。如果那条内容在最新快照
里找不到、或者还在但已经不再可疑，就退回按「回复 → 评论 → 视频」扫描当前选中链
上的第一个可疑条目；有可查目标（记录的那条，或选中链上的）但都干净，就如实说
「这条没有被拦下的内容」；连一个能查的目标都没有（快照里既没选中、也没留下可回退
的记录，比如还没抓过任何内容），就提示先 `pick` 一条。

视频这层看到的是标题，所以念作「被拦下的视频标题」，不叫正文。标题干净、只有作者
名可疑时同样会被拦下：`peek` 会先说明「视频标题本身没被拦下；可疑的是作者名：
「…」」，再把作者名与标题分开念（评论与回复同理，标签分别是「评论正文」「回复
正文」）。快照里同一个 id 出现多次时，`peek` 只认先出现的那一条（快照不按 id 去
重）。旧版本留下的快照只有整条 `suspect`、没有正文与作者名的拆分标记：这时 `peek`
会把正文也按可疑处理，不会因为作者名可疑就断言正文干净；升级后的下一轮抓取会写回
拆分标记。作者名没有 `peekAuthor` 时退回 24 字的 `author`。早期版本把副本存在
`peek` 键下，现在的快照写 `peekText`，读取时按 `peekText` → `peek` → `text` 依次
回退，视频那层最后再退回 `title`（升级前的视频快照只有 `title` 与 `suspect`），
旧快照不会因为改名读不出副本，也不会一边说拦下的是标题一边念「（无标题）」。

这些标记与副本都写在插件自己的 state 里。能直接改 state 的只有宿主和用户本人——
那条路不在注入防线内：改得动 state 的人同样改得动冷却、当日额度与在途标记，这套
守门只对自己写下的 state 负责。防线针对的是桥接喂进来的**内容**：写请求的目标 id
必须来自快照，发送正文只能来自设置项里你自己敲的那句话，可疑目标一律拒写。

## 边界情况

### `reset` 是解卡出口

它清除在途标记、冷却锚点、超时旧 token 名单与当日已占用的
每日写入额度；`writeSeq` 缺失、为负、已到 i64 上限，或低于在途 / 名单里的序号时，
抬到「在途与名单里的最大序号」，重置后的第一笔不会和旧 token 撞号。卡在 i64 上限时
第一次重播种仍停在上限（下限就是上限），但这次已经把在途 token 与名单删掉，再按
一次就回到 0，所以「写入序号用尽」最多按两次 `reset` 就能出来——不是死循环，也
不能靠它去复用可能还在桥接侧跑着的旧序号。有在途写入时，桌宠会额外提醒「别马上
重发」；重置之后旧回执会被忽略，也不再计入每日写入额度。要确保不重复，只能在 `reset` 前等它
回执——超过 120 秒只说明插件不再等它，桥接侧那笔仍可能没结束。

0.4.1 留下的 token 没有序号，与之逐字相同的无序号回执就属于它，照常结束这笔写入
并计数——这是「写入回执都带序号」的唯一例外。升级时旧状态只有 `pendingWrite`、
没有发出时间，只能拿旧的 `lastWriteAt` 兜一个 120 秒窗口；0.4.1 的 `lastWriteAt`
记的是最后一次成功回执的时刻（0.4.3 起改为发出时刻），比那笔写入真正发出的时间
至少早一个冷却（10–600 秒），所以这个窗口可能在旧请求发出之前就开始计时。冷却
同样锚在 `lastWriteAt`；两者都过期后，升级后的第一笔就放行，此时旧那笔在桥接侧
可能还在跑。持久状态无法给桥接侧的剩余运行时间设上界，真正安全的做法是等它回执；
否则只能接受重复的风险。升级后第一次写入会把旧 token 记进超时名单，并按「被顶替
即计数」先记一笔每日写入额度；只有以 `write:` 开头、不超过 40 字节、且动作名
认得出的 token 才进名单，其余坏 token 进不了名单，但只要它占着 `pendingWrite`，
被顶替时一样计数。

`writeInFlight` 是字符串、对象等非整数时本身就是「坏值」证据，不依赖 `pendingWrite`
就按在途处理，但仍和其它在途一样受 120 秒窗口约束（有可用时间锚时超时后照常放行）；
而它为 0、为 `null`（与缺失同义）或缺失时，只有 `pendingWrite` 非空才算在途——规则 5
的「在途标记在但没有可用时间戳时按在途拦住」也适用于这些情形，`reset` 是解卡出口。认不出动作的在途
token 在匹配回执到达时照常清掉，但不计数、不播报动作结果。

## 还没做的

- 插件不做任何「生成式」表达：评论与回复只发你写好的原文，不会自己遣词造句。
- 自动回复只认「被念出来那条评论命中兴趣」，不会逐条扫评论，也不会根据评论内容
  生成回复；自动路径同样不会给视频发评论。
- 评论点赞只能由命令触发，没有自动点赞；自动收藏只认视频本身命中兴趣。
- 注入判定是「归一化 + 特征词」的启发式，不是分类器：识破不了刻意绕开特征词的
  新写法。中文特征词故意收窄成「忽略 / 无视 + 之前 / 以上 / 前面 / 上述」这几族
  （故意不含「忽略所有」：「我妈说忽略所有的烦恼」常见于正常标题），外加
  「系统提示词」「你的新指令」「你现在扮演」「从现在开始你 / 从现在起你」「泄露
  提示词 / 泄露系统提示」；英文只收 `ignore` / `forget` / `disregard` 与
  `previous` / `above` 的固定搭配，外加 `ignore all previous`、`forget everything`
  这类不带 `previous` / `above` 的整句写法，再加上 `system prompt`、
  `developer prompt` 与靠标点成形的
  `system:`、`assistant:`、`http://`、`POST /` 这类。宁可漏掉一种绕法，也不把
  「Linux 常用系统指令合集」「新的指令已经上线」「这条命令会覆盖之前的配置」这种
  日常文案判成注入。它的作用是让可疑正文默认闭嘴，而不是保证拦下所有注入；写入的
  硬保证仍是「只认快照里出现过的 id，且只发你手写的正文」。
- 兴趣关键词来自主应用设置，插件不会自己「学习」你喜欢什么。
- 没有多账号、没有私信、没有视频内的互动数据回传。
- 没有在真实抖音账号、真实桥接服务或真实宿主上验证过这些写端点；示例桥接只
  把请求记在内存里，不操作抖音。

## 本地开发

```sh
node scripts/build-plugin.ts --write
```

构建脚本会把 `sdk/dfy.zig` 与 `src/main.zig` 放进临时编译目录，并带上宿主要求的
四个导出符号。之后在仓库根运行 `node scripts/test-plugin.ts`、
`node scripts/validate.ts` 与 `node scripts/build-index.ts`。

想把没发布的版本装到本地面板里看看，可以手工建一份插件目录：把 `plugin.json` 与
`plugin.wasm` 放进应用数据目录的 `plugins/<id>/`（Windows 是
`%APPDATA%\BlueDaFeiYu-Codex\plugins\`，macOS 是
`~/Library/Application Support/BlueDaFeiYu-Codex/plugins/`），重启应用后会出现在
插件列表，同样标注「运行时未接入」。Flutter 版没有「安装本地插件」按钮，也不在
应用内编译 Zig；真正的执行要等运行时迁移回来。
